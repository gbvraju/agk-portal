# Requirements

Each requirement is a `### REQ-nnn` section with a `- Status:` line (planned | in-progress | done).
Only the Status line may change without an ADR. `done` requires at least one test marker `REQ-nnn` in a
`test_*.py` file under `tests/`.

`REQ-001`..`REQ-099` are reserved for requirements defined by the kit. Add this project's requirements from
`REQ-101`.

### REQ-001 — Protected paths change only with an ADR in the same PR

- Acceptance: AC1 check fails without an ADR that names the path class; AC2 Status-only change in requirements exempt; AC3 message names the path class
- Status: planned

### REQ-002 — Agents never merge or bypass checks

- Acceptance: AC1 branch rules documented in ADR-0001; AC2 settings deny force-push and hard reset; AC3 stop hook blocks on red governance
- Status: planned

### REQ-003 — Every requirement is traceable to tests

- Acceptance: AC1 matrix generated; AC2 done requires a marker; AC3 matrix never committed
- Status: planned

### REQ-101 — The portal reads each person's project facts, read-only

- Acceptance: AC1 Given a signed-in person and a repository the GitHub App is installed on that the person can read, when the page is requested, then the server lists that repository's artifacts and downloads the latest unexpired agk-facts-<week> artifact with the person's own token; AC2 Given a downloaded artifact that holds facts.json with schema 1, when the server reads it, then the facts reach the page unchanged; AC3 Given a facts document whose schema is not 1 or that cannot be parsed, when the server reads it, then the card shows 'not known yet' with that reason and the page still renders; AC4 Given a readable repository with no unexpired agk-facts artifact, when the page is requested, then its card shows 'not known yet' with the reason that no artifact exists for its latest week; AC5 Given the listing or the download of one repository is refused or fails, when the page is requested, then only that repository's card shows 'not known yet' with the HTTP status as the reason, the other repositories are still read, and the page does not fail; AC6 Given a repository the signed-in person cannot read, when the page is requested, then it is never listed, named or counted; AC7 Given any request, when the server calls GitHub, then it makes no write call, uses no token other than the person's own, holds no Claude credential and uses no model; AC8 Given the access proof with a GitHub App user token on a private repository, when it lists and downloads one artifact, then it records each call with its HTTP status and what failed, and if access is refused it stops and adds no personal access token
- Status: planned

### REQ-102 — A person signs in with GitHub and keeps a stateless session

- Acceptance: AC1 Given a visitor who is not signed in, when the page is requested, then the response offers sign-in and shows no project name; AC2 Given a visitor who starts sign-in, when the server redirects to GitHub, then the redirect carries a random state value that is bound to the visitor's browser; AC3 Given a return from GitHub whose state value is missing or does not match the one bound to the browser, when the server handles it, then the sign-in is refused, no token is requested and no session is set; AC4 Given a return with a matching state and a code, when the server obtains the user token, then it sets one cookie that is encrypted and signed, holds the token and its expiry and nothing else, has the flags Secure and HttpOnly and SameSite=Lax, lasts the smaller of 8 hours and the token's expiry, and holds no refresh token; AC5 Given a valid cookie, when a request arrives at any instance of the server, then the person is signed in and no database, key-value store or host storage is read or written; AC6 Given a cookie that is expired or tampered with or missing, when the page is requested, then the person is not signed in, the fixed expiry phrase is shown with an offer to sign in, and no token is used; AC7 Given a signed-in person who signs out, when the server answers, then it clears the cookie, makes no call to GitHub and offers sign-in; AC8 Given a signed-in person with no readable repository on which the App is installed, when the page is requested, then a fixed phrase says so, the page is not blank and no project name is shown
- Status: done

### REQ-103 — The core is portable and each host has one thin adapter

- Acceptance: AC1 Given the core's own TypeScript configuration with the web-worker libraries and no Node types, when the compiler checks site/src/core without emitting, then it succeeds with 0 errors; AC2 Given a core file that uses a Node-only global such as process or Buffer, when the same check runs, then it fails and names the file; AC3 Given every file under site/src/core, when the import scan reads its syntax tree, then every import and every re-export and every dynamic import is a relative path that resolves inside site/src/core and the core has no runtime dependency; AC4 Given a core file that imports a Node module or a Cloudflare module or a package, when the import scan runs, then it fails and names the file and the specifier; AC5 Given a core that needs a secret or a setting, when it runs under a test configuration, then it asks only through the configuration interface for names on the one documented list and reads no environment variable, binding or global for it; AC6 Given a setting missing from the configuration, when the core needs it, then it refuses with a message that names the setting and never its value; AC7 Given the Cloudflare adapter with a fake environment and a fake request, when it handles the request, then it fills the configuration from the fake environment's secrets and variables, passes the request to the core and returns the core's response unchanged; AC8 Given the Cloudflare adapter, when it hands anything to the core, then it hands no environment object and no Cloudflare binding, only the request and the configuration interface
- Status: planned

### REQ-104 — Responses are secure by default and the server never writes to GitHub

- Acceptance: AC1 Given any response of the server whether a page or the stylesheet or a redirect or a refusal, when it is sent, then it carries the strict Content-Security-Policy with no unsafe keyword and the headers X-Content-Type-Options nosniff and Referrer-Policy no-referrer and Strict-Transport-Security; AC2 Given any signed-in or sign-in response, when it is sent, then it carries Cache-Control no-store and the page holds no script and no inline style; AC3 Given the OAuth callback with a code and a state, when the server completes or refuses it, then it answers with a 303 redirect to the home page and the code and the state are in no URL it sends; AC4 Given the sign-in and session and sign-out and failure paths run with fixture tokens and codes and a session key, when every console and log output is captured, then none of those values appears in it and no error detail reaches the response; AC5 Given every response and every outbound GitHub request of those paths, when they are checked, then no token and no code and no cookie value is in a URL and GitHub calls carry the token only in the Authorization header; AC6 Given the committed github-app-manifest.json, when the test reads it, then its permissions are exactly actions read and metadata read and nothing else and expire user authorization tokens is on; AC7 Given the installation listing the server fetches for a person, when an installation grants any permission beyond actions read and metadata read or any write, then the server refuses to serve that person with a fixed phrase and shows no project; AC8 Given every outbound request the server makes to GitHub, when its method and address are checked, then each is a GET except the one POST of the sign-in token exchange to its exact address, and any other method or POST address is refused before it is sent
- Status: planned

### REQ-105 — The This week section follows the weekly report's rules

- Acceptance: AC1 Given a project's facts and the ISO week named by its artifact, when the page shows This week, then the week runs from Monday to Sunday in UTC and the section has five parts in order, Delivered and Proven and Needs your decision and At risk and What it cost, each computed from the facts exactly as the weekly report computes its part of the same name; AC2 Given each fixture facts document and week, when the items and numbers of the five parts are compared with the output of the repository's scripts/agk/product_report.py for the same document and week, then every item and count and hour total and link equals the report's and stands in the report's order; AC3 Given every line of the five parts, when it is shown, then it is a fixed phrase from the spec's list over a facts number or a requirement's own title and ends with a link to its evidence on GitHub, and no pull request title and no free text of a residual or a specification or a decision is shown as a sentence; AC4 Given a part with no item, when the page is shown, then it says the fixed phrase Nothing this week for that part and for no other reason; AC5 Given a value that the facts mark unknown, when the page is shown, then it says not known yet with the count of items lacking it and never shows zero, and a sum with an unknown term is not shown as a number; AC6 Given facts whose dirty flag is not false, when the page is shown, then it shows the fixed notice that the working tree was modified and the facts commit as a link; AC7 Given a week in which more than ten pull requests merged, when Delivered and What it cost are shown, then each shows its one summary line with the week link and no line per pull request; AC8 Given a project whose facts cannot be read or whose repo is unknown, when the page is shown, then This week is not shown for it and only its card says not known yet
- Status: planned

### REQ-106 — The Requirements section shows how each requirement stands

- Acceptance: AC1 Given a project's facts, when the Requirements section is shown, then each requirement numbered REQ-100 or above appears once as one line with its own title and a status phrase of planned or in progress or done, and its identifier after the sentence as a reference linked to its line in docs/requirements.md at the facts commit; AC2 Given a requirement's criteria and the facts' markers, when its line is shown, then it says how many of its acceptance criteria have a test by the report's rule that a marker names the requirement and the criterion, and it never says that a test is good; AC3 Given the facts' specs, when a requirement's line is shown, then its specification phrase is approved or waiting for approval or none by the report's rule that a spec names the requirement, and its proven phrase is the one the Proven part of This week gives the same requirement; AC4 Given the listed requirements, when the section is shown, then they stand in the groups In progress and Planned and Done with their counts in that order and in id order inside each group, and a Done group of more than ten is closed behind a details element; AC5 Given a requirement's details element, when it is opened, then it lists the requirement's own criteria text each with its test mark or the phrase no test, and a requirement with no criteria or with unknown criteria says so in a fixed phrase; AC6 Given the requirements numbered REQ-001 to REQ-099, when the section is shown, then none of them is listed and the fixed line saying how many kit requirements are not shown appears with its link; AC7 Given a value that the facts mark unknown, when the section is shown, then it says not known yet and never shows zero or a guessed status, and a source that cannot be read shows one fixed line in place of its lines; AC8 Given a project whose facts cannot be read, when the page is shown, then Requirements is not shown for it and only its card says not known yet
- Status: planned

### REQ-107 — The Trend section shows how each measure moves week by week

- Acceptance: AC1 Given the latest facts artifact and no other download, when the Trend section is shown, then it shows up to seven weeks, the artifact's week and the six weeks before it, all computed from that one document, and it makes no further request to GitHub for them; AC2 Given a week and one of the measures changes merged and time from opening to merge and review rounds and estimates within range and changes sent back or merged late and requirements done to date, when its value is computed, then it equals the value the report gives for that week when it is run with the same week on the same document; AC3 Given each measure, when it is shown, then it is one short block with this week's value and a fixed phrase of up from or down from or same as last week and then the earlier weeks on one compact line newest first, with no table and no chart and no script and no horizontal scroll at 360 px width; AC4 Given the measure requirements done to date, when a week is computed, then it counts the requirements with status done whose done date falls on or before the end of that week, and a done requirement with no known done date makes the count not known yet; AC5 Given a measure that is a snapshot of the report date and cannot be rebuilt for an earlier week, when the earlier weeks are shown, then each reads not known yet and the spec lists those measures; AC6 Given a week outside the facts window or a week with an unknown source value, when the trend is shown, then that week reads not known yet and is never shown as zero or filled in, and a rise or fall is stated only between two known weeks; AC7 Given fewer than two known weeks, when the section is shown, then it says Not enough history yet and states no rise or fall; AC8 Given every line of the section, when it is shown, then it is a fixed phrase over a facts number and ends with a link to its evidence on GitHub and says time from opening to merge and never cost or effort alone, and a project whose facts cannot be read shows only its card
- Status: planned
