# SPEC-0007: The Trend section shows how each measure moves week by week

- Status: Draft
- Owner: maintainers
- Requirements: REQ-107

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence, as data: "The Trend section compares a project's last weeks, each computed from that week's facts artifact by the weekly report's own rules, showing each measure per week with a fixed phrase for whether it rose, fell or stayed the same, a week without facts shown as not known yet, each linked to its evidence." It is milestone M2 of ADR-0002 as amended by ADR-0006, third part (This week is SPEC-0005, Requirements is SPEC-0006). The product owner answered three questions on 2026-10-21: the five measures and requirements done to date, each by the report's own rule; neither a wide table nor a chart, because the page is mobile first with no horizontal scroll at 360 px (milestone M3): one short block per measure, with this week's value and "up from {n}", "down from {n}" or "same as last week", then the earlier weeks as one compact line, newest first, server-rendered with no script; and **one artifact, not eight**: every week's values are computed from the latest `agk-facts-<week>` artifact alone, which holds the last eight weeks of pull requests (`--weeks 8`), and the report can render any of those weeks from that one document (the parity test runs `product_report.py --week W` on it). The requirements done per week come from `done_on`. A measure that is a snapshot of the report date and cannot be rebuilt for an earlier week reads "not known yet" for the earlier weeks, and each is listed in rule 5. There are no extra downloads per request. The page follows the weekly report's own rules (SPEC-0005); the report has no trend, so the weekly values are the report's own functions applied to each week's window of the same document.

## Rules

1. **One document, seven weeks.** The section reads the latest artifact's `facts.json` that SPEC-0001 rule 2 already downloaded for This week, and makes no other request for it. The weeks shown are the artifact's week W (the label of the artifact, Monday to Sunday UTC) and the six weeks before it, newest first. The facts window starts on the Monday seven weeks before the Monday of the week of the facts' `today` (agk SPEC-0009 rule 14; `window_start` in `facts.py`, `--weeks` 8 by default, which the kit's `product-report` workflow does not change, agk SPEC-0011 rule 15 (verify)). A week that starts before the window's start reads "not known yet". When the facts state their own window (a field the kit will add, Q-S0007-2), the page reads it instead of the kit's default. The eighth week of the window, the report date's own unfinished week, is not shown: the report does not cover it (agk SPEC-0011 rule 8).
2. **The weekly value is the report's own function.** For a week W' with start `s` and end `e` (the next Monday), each value is computed by the report's function for the same window (`week_window`), from the same facts fields, so that it equals what `product_report.py --facts FILE --week W'` reports (agk SPEC-0011 rules 9 and 10):
   - *Changes merged* is the number of pull requests with `state` `merged` and `merged_at` inside the window (`merged_in_week`; the Delivered count, agk SPEC-0015 rule 1).
   - *Time from opening to merge* is the sum of the hours from `created_at` to `merged_at` of those pull requests, rounded half-up to 0.1 each (`hours_between`; Cost, agk SPEC-0011 rule 10), summed in whole tenths of an hour.
   - *Review rounds* is the sum of their `fix` verdicts (`verdict_count`; Cost).
   - *Estimates within range* is "{N} of {M} within range", or "none declared this week" when M is 0 (`estimate_ending`; agk SPEC-0018 rule 6). Its comparison is of the share N/M between two weeks that both declare estimates, compared as exact fractions.
   - *Changes sent back or merged before review* is the number of different pull requests that At risk names for the window as *sent back* (closed in the window with two or more `fix` verdicts or any `rejected`) or as *merged with no verdict* or *merged before its last commit was cleared* (`at_risk`, `verdict_count`, `cleared_line`; agk SPEC-0011 rule 10, SPEC-0016 rule 1). This is the part of At risk that can be rebuilt for a past week (Q-S0007-1).
   - *Requirements done to date* is rule 4.
   A week with no pull request merged shows "Nothing this week." for the time, the review rounds and the estimates, as the report prints "nothing this week" for Cost, and 0 changes merged; for a rise or fall, "nothing" counts as 0 hours and 0 rounds and is not compared for estimates.
3. **The blocks.** One block per measure, in this order: Changes merged, Time from opening to merge, Review rounds, Estimates within range, Changes sent back or merged before review, Requirements done to date. A block has a heading (the measure's name), one line with the artifact's week value and the fixed phrase of rule 8 comparing it with the previous week, and one compact line with the earlier weeks, newest first, as "{week label}: {value}" separated by "; ". The previous week for the comparison is the nearest earlier week with a known value; the phrase names it when it is not the week before ("up from {n} in {label}"). No table, no chart, no script, no inline style (SPEC-0004 rules 1 and 2); the lines wrap, and nothing needs a horizontal scroll at 360 px width.
4. **Requirements done to date.** For a week with end `e`, the count of `requirements[]` with `status` `done` whose `done_on` is a date before `e` (`done_on`, agk SPEC-0017 rule 1 and SPEC-0009 rule 8; `delivered` of the report reads it with `day_of`). A `done` requirement whose `done_on` is `"unknown"` or missing cannot be placed in a week, so the count is "not known yet" for every week with such a requirement, with the count of those requirements ("{k} requirements lack a date"). It counts the requirements that are done now; a requirement that was done and is not done now is not counted (residual).
5. **Snapshot measures: not known for earlier weeks.** These measures describe the report date, not a week, because the facts hold only their present state and no history; for an earlier week each reads "not known yet". The artifact's own week shows its value:
   - overdue residuals (`residuals[]` open and past `due` as of `today`);
   - open pull requests older than seven days (open as of `today`);
   - the drift findings, "housekeeping checks" (`drift` as of the facts commit);
   - the items that wait for a decision of Needs you: draft specifications, proposed decisions, waiting questions, changes without a verdict, planned requirements with no specification (the present state of each);
   - the planned and in-progress requirements and the tests per criterion (the present `status` and `markers`).

   Only the first three are shown in Trend, in a last block "Only known for this week" with the fixed phrases of rule 8 and the line "Earlier weeks: not known yet."; the others are listed here so that no one asks for them: they stay in This week (SPEC-0005) and Requirements (SPEC-0006).
6. **Unknown, never zero.** A value the facts mark `"unknown"` (a pull request's `merged_at`, `created_at`, `verdicts`, `estimated_hours` or `actual_hours`, or `done_on`) makes that week's value for that measure "not known yet ({k} of {n} changes lack it)" where it is a sum, never zero and never a number (agk SPEC-0011 rule 12). A week with an unknown `pull_requests` source reads "not known yet" for every measure. A rise or fall is stated only between two weeks that are both known. A week that is "not known yet" is shown in its place in the earlier-weeks line.
7. **Not enough history.** With fewer than two known weeks in the section the section says "Not enough history yet." and states no rise or fall. With no known week, only that sentence is shown. A project whose facts cannot be read, whose `repo` is `"unknown"` or whose `schema` is not 1 shows no Trend, only its card (SPEC-0001 rule 4; SPEC-0005 rule 9).
8. **The fixed phrases.** These, and no other sentence, are shown. The label for time is always "time from opening to merge", never "cost" or "effort" alone. A count of one uses the singular.

   | Part | Fixed phrase |
   | --- | --- |
   | Section | "Trend" ; "Weeks {first label} to {last label}, from the facts of week {label}." ; "Not enough history yet." |
   | Headings | "Changes merged" / "Time from opening to merge (hours)" / "Review rounds" / "Estimates within range" / "Changes sent back or merged before review" / "Requirements done to date" / "Only known for this week" |
   | This week | "{v}, up from {n}." / "{v}, down from {n}." / "{v}, same as last week." / "{v}, up from {n} in {label}." / "{v} (no earlier week is known)." |
   | Values | "{n}" ; "{h} hours" ; "{n} of {m} within range" ; "none declared this week" ; "Nothing this week." ; "not known yet" ; "not known yet ({k} of {n} changes lack it)" ; "not known yet ({k} requirements lack a date)" |
   | Earlier weeks | "Earlier weeks: {label} {v}; {label} {v}; …" ; "Earlier weeks: not known yet." |
   | Only this week | "Overdue items: {n}." / "Changes open for more than seven days: {n}." / "Housekeeping checks: {n} issues found." (the D-codes only behind the link) |

   The phrases are held to the plain-language standard of SPEC-0005, and the product owner reviews this table in the approval pull request before the spec is approved.
9. **Links.** Every line ends with a link to its evidence, built from the facts' `repo` and `commit` as the report builds them (agk SPEC-0011 rule 11): the merged-in-the-week search for the changes and time and review rounds of a week (`https://github.com/{repo}/pulls?q=is%3Apr+is%3Amerged+merged%3A{start}..{end}`), `docs/requirements.md` at the facts commit for the requirements, the open drift issue or the directory for the housekeeping line, and the pull request for a named change.
10. **The parity tests.** For each fixture, and for each of its seven weeks, the tests render the weekly value of every measure and run `python3 scripts/agk/product_report.py --facts FILE --week WEEK` on the same pair. They compare the changes merged with the Delivered lines of the report, the time and the review rounds with the totals line of Cost (`hours in total`, `fix verdicts in total`), the estimates with its `estimate:` ending, the changes sent back or merged before review with the pull requests named by At risk for the kinds of rule 2, and the requirements done to date with the requirement lines of Delivered of the weeks up to it. A test changes one number in a fixture and shows that only the values that depend on it change. A test shows that the section makes no request for a second artifact.
11. **Fixtures and tests.** The fixtures are facts documents under `site/tests/fixtures/` with no token and no signed address, covering seven full weeks of merged pull requests with different hours, verdicts and estimates, an empty week, a busy week, a week before the window, unknown values in each field of rule 6, requirements done in different weeks, a done requirement with no `done_on`, and a document with fewer than two known weeks. The tests are TypeScript files named `*.test.ts` under `site/tests/`, run by the npm command in `agk.toml` `project_tests`, each carrying the marker `REQ-107 ACn` it proves. They need Python for the parity tests only.

## Tests

- Rules 1 and 10: the section shows up to seven weeks from one document, the artifact's week first, and a second download is never made; REQ-107 AC1.
- Rules 2 and 10: for each fixture week each measure equals the report's value for the same week; REQ-107 AC2.
- Rule 3: one block per measure with this week's value and the right fixed phrase, the earlier weeks on one line newest first, no table, no chart, no script, and no element wider than 360 px; REQ-107 AC3.
- Rule 4: the count of done requirements up to each week from `done_on`, and "not known yet" when a done requirement has no date; REQ-107 AC4.
- Rule 5: each snapshot measure reads "not known yet" for earlier weeks and shows its value for the artifact's week only; REQ-107 AC5.
- Rules 1 and 6: a week before the window, an unknown value and an unknown source each read "not known yet", never zero, and a rise or fall is stated only between two known weeks; REQ-107 AC6.
- Rule 7: fewer than two known weeks says "Not enough history yet." and states no rise or fall; REQ-107 AC7.
- Rules 8 and 9: every line is a fixed phrase, ends with a link, and says "time from opening to merge"; a project without readable facts shows only its card; REQ-107 AC8.

## Proof

REQ-107 AC1 and AC2: *the trend is the report's own numbers, week by week, from one download.* Rules 1, 2 and 10. REQ-107 AC3: *it reads on a phone.* Rule 3. REQ-107 AC4 and AC5: *what history cannot give is said.* Rules 4 and 5. REQ-107 AC6 and AC7: *an unknown or a short history never shows as zero or as a trend.* Rules 6 and 7. REQ-107 AC8: *plain fixed phrases, honestly labelled, each linked.* Rules 8 and 9. The maintainers read one live Trend beside the report issues of the same weeks before the milestone is called done.

## Residual

Until this project upgrades to that kit version, the spec reads the kit's default of eight weeks (`--weeks` 8, which the kit's workflow does not change); when the field exists, the page reads it (due 2026-12-31).
- 2026-10-21: requirements done to date counts the requirements that are done now by their `done_on`; a requirement that was done and then reopened is not counted for the weeks it was done, because the facts hold no status history (due 2026-12-31).
- 2026-10-21: the page is tied to the report as vendored at kit 0.32.0 and to the facts fields of agk SPEC-0009; a kit upgrade that changes either fails the parity tests, and the spec is then amended (due 2026-12-31).
- 2026-10-21: the drift findings, the overdue residuals and the open pull requests have no history in the facts; a history would need the facts of earlier weeks (the earlier `agk-facts-<week>` artifacts, 90 days of them), which this slice does not download (due 2026-12-31).
- 2026-10-21: the product owner reviews the phrase table of rule 8 in the approval pull request, with SPEC-0005's plain-language standard, before this spec is approved (due 2026-11-30).
