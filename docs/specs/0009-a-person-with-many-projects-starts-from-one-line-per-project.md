# SPEC-0009: A person with many projects starts from one line per project

- Status: Approved
- Owner: maintainers
- Requirements: REQ-109

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence, as data: "A person with many projects starts from one line per project, grouped by whether it needs attention, and opens one project's week from its line." It is the issue #51 brief of the maintainers (2026-10-24): the approved mockup is the reference, the start page lists every project on one line, grouped, and each line opens that project's week. The maintainers answered 3 questions before it was written: (1) a project whose latest report has no counts (a report of schema 1 or 2) stands under Not known yet, with the reason "the report has no counts (made by an older kit)", and its totals read not known yet; (2) only a report whose week is the previous ISO week or the current one is grouped by its counts, a project whose latest report is older stands under Not known yet with the reason "the latest report is for week {week}", and this compares week labels only, nothing being computed from the data; (3) the start page is `/`, a project's page is `/p/{owner}/{repo}`, a person with one project still sees the list, the reads per project are recorded from a test with a counting client, and the time to first byte on staging is recorded by the maintainers after the merge. SPEC-0001 (the person's projects and their facts), SPEC-0004 (security) and SPEC-0008 (the look) stay as they are; the fixed phrases of this page are listed in rule 6 and are this spec's own. The page computes nothing from the data: it places the report's own numbers and groups by them.

## Rules

1. **The start page.** `/` for a signed-in person lists the projects of SPEC-0001 (the repositories the person can read through the installations), one line each, in the order of that list (sorted by name). A line holds the project's name (`owner/repo`), the week of its latest report, the counts `delivered`, `needs_you` and `at_risk` of the report's `counts` (schema 3; a count of `"unknown"` reads "not known yet"), the figures `merged` and `hours` of the item of kind `week-totals` of its `cost` section (an `hours` of `unknown`, or no such item, reads "not known yet"), and a link to `/p/{owner}/{repo}`. The numbers are the data's own, placed as they are; none is added up, compared or rounded. A signed-in person with no project sees the existing empty phrase; a person with one project still sees the list.
2. **The groups.** Three groups, in this order, each under its heading: "Needs your attention", "On track", "Not known yet". A project whose report is readable, is of schema 3 and is for the current or the previous ISO week is placed by its counts: `needs_you` or `at_risk` above 0 or `"unknown"` stands under Needs your attention, every other under On track. This is the page's only rule over numbers. Within a group the projects keep the order of the person's list. A group with no project is not shown.
3. **Not known yet.** A project stands under Not known yet, with its reason and with no number of it, when: its facts or its report cannot be read or are absent (the card's existing reasons, SPEC-0001 and SPEC-0005 rule 13); or its latest report is for a week that is neither the current nor the previous ISO week, reason "the latest report is for week {week}"; or its report is of schema 1 or 2, reason "the report has no counts (made by an older kit)". The reasons are tried in that order. The current ISO week is the week label of the UTC clock the core already has (`core.now`), the previous the label of the week before it; a report's week is the label of its artifact. Only labels are compared; nothing is computed from the data.
4. **Counts of zero.** A count of 0 is shown muted (the `muted` colour) on a wide screen and is not shown on a phone (a width below 600 px); a count above 0 or `"unknown"` is always shown. The count is then not a number the page decided: the CSS only hides what the data says is 0.
5. **A project's page.** `/p/{owner}/{repo}` for a project of the person's list shows that project's This week (today's card) and a link "All projects" to `/`. A name that is not an owner and a repository of the allowed shape, or a project that is not in the person's list, is answered "Page not found" (the existing page) and no read of GitHub is made for it.
6. **Find a project, and the phrases.** A form `GET /` with one native text input `q` and a button "Find a project" keeps the lines whose `owner/repo` contains q, ignoring case; q is trimmed, at most 100 characters (longer is cut), escaped wherever it is shown, and an empty q keeps every line. A query that matches nothing says "No project matches." No script is used. The fixed phrases of this page, and no other, are: the title and heading "Your projects" (SPEC-0005 rule 10), "All projects", "Find a project", "Needs your attention", "On track", "Not known yet", "No project matches.", the labels of a line "delivered", "needs you", "at risk", "merged" and "hours", and the reasons of rule 3 and the card's.
7. **The reads.** The start page reads each project's facts and report with the reads of SPEC-0001 and SPEC-0005 (listing, download, archive), in parallel, as the cards do; a failure of one project is that line's and stops no other. A test with a counting client records the number of GitHub reads per project and the page for 3 projects in `docs/runs/start-page-reads.md`. No claim is made about 50 projects before the maintainers have recorded the time to first byte of the start page on staging, with the projects configured there, in `docs/runs/`.
8. **The look and the security.** SPEC-0008 applies in full: every colour is a token of the one stylesheet, only classes and no `style` attribute, no script, native controls only with a focus ring and a 44 px target, one column at 360 px without a horizontal scroll, readable from a phone to a wide screen. The responses and headers are SPEC-0004's, unchanged; the `q` and the project name are the only request text shown and are escaped.

## Tests

- Rules 1 and 2: each project is one line with its name, week, counts and totals, linked to its page, and the groups and their order follow the counts; REQ-109 AC1, REQ-109 AC2.
- Rule 3: unreadable facts, a report without counts and an older week each stand under Not known yet with their reason and no number; the current week and the previous week are grouped by counts, including across a year boundary and an ISO week 53; REQ-109 AC3.
- Rule 4: the stylesheet mutes a 0 on a wide screen and hides it below 600 px, and an unknown or positive count is never hidden; REQ-109 AC4.
- Rule 5: a listed project's page shows its This week and the link back, and a name not in the list or of a bad shape answers Page not found with no read of GitHub; REQ-109 AC5.
- Rule 6: the find form keeps the matching lines ignoring case, escapes q, cuts it at 100 characters, says No project matches, and sends no script; REQ-109 AC6.
- Rule 7: a counting client records the reads per project and the page for 3 projects in docs/runs; one failing project does not stop another; REQ-109 AC7.
- Rule 8: the tokens, no script, no style attribute, native controls, 44 px and 360 px; the headers are unchanged; REQ-109 AC8.

## Proof

REQ-109 AC4: *a zero is quiet.* Rule 4. REQ-109 AC5 and AC6: *one project's week opens from its line, and a project can be found.* Rules 5 and 6. REQ-109 AC7: *no claim about many projects before it is measured.* Rule 7. REQ-109 AC8: *it looks and is as safe as the rest of the page.* Rule 8.
