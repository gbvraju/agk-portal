# SPEC-0010: A person sees what waits for them and opens it on GitHub

- Status: Approved
- Owner: maintainers
- Requirements: REQ-110

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence, as data: "A person sees what waits for them: specs to approve and pull requests ready to merge, each with its verdict, and opens them on GitHub from the page." It is the issue #64 brief of the maintainers (2026-10-25), whose five answers are the conductor's proposals, each open to the maintainers' ruling in the questions below. In agk a person approves every spec (an `Approve: <head> SPEC-<n>` comment) and merges every pull request; the router labels a pull request `agk:approve` or `agk:ready` when it waits for a person, and the weekly report shows "Ready to merge" only once a week, which is too late for work that is ready now. The principles that bind every rule: the page stays read-only (a link opens GitHub; no button merges, approves or comments); it reads only what the project publishes or what GitHub shows publicly; no token is in the page; nothing names one project. Where the brief left a point open, this spec took the most conservative reading and recorded the point as a question; the maintainer ruled the nine questions on 2026-10-26 (in the conductor session, posted on pull request #65 by the conductor), and each ruling is applied below and recorded under Open questions. Rulings 1, 2 and 4 to 9 accept the conductor's recommendations; ruling 3 is the maintainer's own: "the verdict should always be in business meaning, easily understandable".

## Rules

1. **The cockpit.** A signed-in person's cockpit, at `/cockpit` (Q-S0010-4), linked from the start page and the project pages by the word "Cockpit" (also the page's title and heading), shows three parts in this order, each under its fixed heading: "Needs your merge", "Specs to approve", "In the pipeline". Each part is built from the projects of SPEC-0001 rule 1 (the repositories on which the App is installed and that the person can read), in the order of that list, and shows nothing of a repository the person cannot read. A part groups its lines under the project's name (`owner/repo`). The cockpit is read-only (rule 8).
2. **The pipeline data.** For each project the page reads one document, the pipeline document, which the project publishes as a workflow artifact of its own named `agk-pipeline` (Q-S0010-1, Q-S0010-2): agk's router writes it after every routing run, so it is current, and the page reads the newest unexpired one as SPEC-0001 rule 2 reads the facts, listing the repository's artifacts, downloading the archive through the redirect and reading it. The archive holds exactly one entry, `pipeline.json`; any other entry, a missing one or a damaged one refuses the archive. It is read with the signed-in person's own token and the App's two declared read permissions (SPEC-0004 rules 6 and 7): no permission is added, the portal reads no pull request, label or comment itself, and the browser reads nothing. The weekly report and its schema do not change. The closed list is agk's pipeline schema 1 (`kit/pipeline-schema.json`, agk SPEC-0036 rule 2): exactly the keys `schema` (the number 1), `as_of` (a UTC time `YYYY-MM-DDTHH:MM:SSZ`), `ready`, `approve` and `counts`; every item of `ready` exactly `number` (an integer), `summary` (a plain sentence for a person who is not a developer, from the `Summary:` line of the pull request body, or the word `unknown`) and `url` (an address starting `https://`); every item of `approve` exactly `number`, `spec` (`SPEC-` and four digits, or `unknown`), `spec_title` (the spec's own title, or `unknown`) and `url`; and `counts`, exactly the six keys `review`, `fix`, `ci-red`, `conflict`, `approve` and `ready` (Q-S0010-7: a closed list, a new label is a new schema), each an integer from 0 or `"unknown"`. The page checks the document against that list as SPEC-0005 rule 13 does the report: an extra or missing key, a wrong type, a count below 0 or not whole, or an `unknown` where the list does not allow it makes that project "not known yet" with the reason "the pipeline document could not be read"; a JSON object whose `schema` is an integer other than 1 says "the pipeline document has a schema this page does not read"; no artifact says "no pipeline document exists"; a failed read says the reason of SPEC-0001 rule 6. A failure is that project's alone.
3. **Needs your merge.** One line per item of `ready`, in the order of the data: "{summary}: reviewed, ready to merge", the whole line linked to the pull request. `{summary}` is the data's `summary`, escaped and cut at 120 characters with an ellipsis. With no `summary` in the data the line is "Pull request #{n}: reviewed, ready to merge". The raw verdict line is never shown: no `Verdict:` text and no commit identifier appear on the page, which speaks in business words only (Q-S0010-3). The title of the pull request is not shown.
4. **Specs to approve.** One line per item of `approve`, in the order of the data, the whole line linked to the pull request. With a `spec_title` the line is "{spec title}: waits for your approval", the title escaped and cut at 120 characters with an ellipsis. With a `spec_title` of `unknown` and a `spec` of the shape `SPEC-` and four digits it is "Pull request #{n} asks for approval of {spec}". With both `unknown` it is "A spec waiting for approval could not be read: not known yet." (SPEC-0005 rule 10).
5. **In the pipeline.** One strip per project: "{project}: review {n}, fix {n}, ci red {n}, conflict {n}, approve {n}, ready {n}", each count the data's own, in this order, a count of `"unknown"` reading "not known yet" in its place; it is a count and never a list, and the page adds nothing up. A count of 0 is a known value and is shown muted as SPEC-0009 rule 4 shows it (muted on a wide screen and not shown on a phone, a width below 600 px; a count above 0 or `"unknown"` is always shown), Q-S0010-8. A project with nothing waiting stands in this strip only and in no other part (Q-S0010-9).
6. **Empty and unknown.** A part whose lists are empty for every project says "Nothing waits for you." (the strip is never empty); a project with nothing in a list is left out of that part and is not named in it. A project with no pipeline data, with data that cannot be read, or whose read failed stands under each part with "{project}: not known yet: {reason}", with no number of it, never as zero and never as an empty part; a failure of one project is that project's and stops no other (SPEC-0001 rule 6). The page computes no count: a number is shown only if the data states it.
7. **As of.** Each project's block shows "as of {as_of}" with the data's own value, placed as it is; no age is computed from it, no limit applies and no data is hidden for being old (Q-S0010-6).
8. **Read-only, and the links.** The only way to act is a link. A link is shown only if its address starts with `https://github.com/` and holds no space or quote (SPEC-0005 rule 9); any other address is not shown and the line stays as text. There is no form that changes anything, no button that merges, approves or comments, no script, no token in the markup, and the server makes no call to GitHub that writes (SPEC-0001 rule 3, SPEC-0004 rule 8). Nothing names one project: no project, owner or repository is written in a file of this repository.
9. **The look and the security.** SPEC-0008 applies in full (tokens, classes only, native controls, a 44 px target, one column at 360 px without a horizontal scroll, a fold over 5 lines of a list, a count of lines for layout and not a figure, Q-S0010-5: the lines of one project's list in a details element whose summary is the project's name and the number of its lines, "{project} ({n})") and so do SPEC-0004's headers; every text from the data is escaped.
10. **The fixed phrases.** These, and no other sentence, are shown: the headings "Needs your merge", "Specs to approve" and "In the pipeline", "Cockpit", "All projects", "Nothing waits for you.", "{summary}: reviewed, ready to merge", "Pull request #{n}: reviewed, ready to merge", "{spec title}: waits for your approval", "Pull request #{n} asks for approval of {spec}", the strip "{project}: review {n}, fix {n}, ci red {n}, conflict {n}, approve {n}, ready {n}", "as of {as_of}", "A spec waiting for approval could not be read: not known yet.", "{project} ({n})" (the summary of a fold), "not known yet", and the reasons of SPEC-0001 and SPEC-0005 rule 13 for a project that cannot be read. The `summary` and the `spec_title` are sentences of the data, escaped and cut at 120 characters; this is the exception to SPEC-0005 rule 10 that the maintainer's ruling on Q-S0010-3 makes for this page (SPEC-0005's rule 10 binds the This week section, which it does not change). No title of a pull request is shown.

## Tests

- Rule 3: each item of `ready` is one line "{summary}: reviewed, ready to merge" (escaped, cut at 120 characters, linked), or "Pull request #{n}: reviewed, ready to merge" with no summary, in the order of the data, and no verdict text, no commit identifier and no title is shown; REQ-110 AC1.
- Rule 4: each item of `approve` is one line "{spec title}: waits for your approval" (escaped, cut, linked), or "Pull request #{n} asks for approval of {spec}" with a title of `unknown`, or the unknown line with both `unknown`, in the order of the data; REQ-110 AC2.
- Rule 5: the strip shows the six counts in order, an unknown count reads not known yet, a 0 is muted on a wide screen and not shown on a phone, no list is shown, and a project with nothing waiting stands in the strip only; REQ-110 AC3.
- Rule 6: empty lists say "Nothing waits for you.", and a project with absent, unreadable or failed data stands with not known yet and its reason, never as zero; REQ-110 AC4.
- Rule 2: the newest unexpired `agk-pipeline` artifact holding exactly `pipeline.json` is read with the person's token, and a document that departs from agk's closed list, a schema other than 1, no artifact, a damaged archive or a failed read is "not known yet" with its reason; REQ-110 AC4, REQ-110 AC6.
- Rules 1, 2 and 8: no form, button or script is in the markup, no token is in the page, a link not of GitHub is not shown, the server makes only reads with the person's token, and only the projects of the person's list are shown; REQ-110 AC5, REQ-110 AC6.
- Rule 7: the as-of is the data's own and no age is computed; REQ-110 AC7.
- Rule 9: the tokens, no script, no style attribute, native controls, 44 px and 360 px; the headers are unchanged; REQ-110 AC8.
- All tests use fixtures of saved responses and no network.

## Open questions

- Q-S0010-1 The brief's open point 4: where does the data come from? The facts are these. The App has exactly the permissions Actions read and Metadata read, and the server refuses an installation with any other (SPEC-0004 rules 6 and 7); GitHub's labels and comments of a pull request need Pull requests read (verify), so reading them from the server needs a SPEC-0004 amendment, a new App permission that every installation must accept, and an update of the permission check. Reading GitHub's public API from the browser is excluded by SPEC-0004 rules 1 and 2 and SPEC-0008 (strict policy, no script), reads public repositories only and shares one anonymous rate limit. Publishing a document in a workflow artifact needs no new permission (the portal already reads artifacts) but needs agk to write it. The criteria assume the last: the project publishes the pipeline document. Confirm, or rule the server read (with the permission amendment) or another source.
  Ruled 2026-10-26 by the maintainer: the project publishes the pipeline document as an artifact. No App permission is added, and the browser reads nothing.
- Q-S0010-2 If the project publishes it: under what name and how often? The weekly `agk-facts-<week>` artifact is the wrong carrier for work that is ready now (it is made once a week), and SPEC-0001 rule 2 refuses an archive with a third entry. The criteria assume a separate artifact of its own (name to be fixed by agk, for example `agk-pipeline`), the latest unexpired one read as the facts are, written by the router or a scheduled job at a cadence agk chooses; schema 6 of the report does not change. Confirm, or rule another carrier, and say who writes agk's requirement and schema (the portal's build waits for it and for a golden of it).
  Ruled 2026-10-26 by the maintainer: a separate artifact, `agk-pipeline`. agk's router writes it on every label change, so it is current, and the page reads the latest unexpired one. The weekly report and its schema do not change. agk writes the requirement and the schema (an agk brief), and the portal's build waits for its golden.
- Q-S0010-3 The verdict line is free text from a comment. The criteria show the first line, escaped and cut at 120 characters. Confirm, or rule that only a fixed word ("cleared", with the head) is shown, or another length.
  Ruled 2026-10-26 by the maintainer (his own words: "the verdict should always be in business meaning, easily understandable"): plain business words, never the raw verdict line. No `Verdict: cleared <sha>` and no sha appear on the page. Needs your merge: "{summary}: reviewed, ready to merge", where `{summary}` is one plain sentence, written for a non-developer, that the data gives for the pull request (agk adds a `Summary:` line to every pull request body for it), escaped and cut at 120 characters. Specs to approve: "{spec title}: waits for your approval", the spec's own title, which the data gives. With no summary or no title in the data the line is "Pull request #{n}: reviewed, ready to merge" or "Pull request #{n} asks for approval of {spec}". The summary and the spec title are allowed as data sentences, escaped, as the exception to SPEC-0005 rule 10 that this ruling makes.
- Q-S0010-4 Where is the cockpit? The criteria put it at its own address `/cockpit`, linked from the start page and the project pages. Confirm, or rule that it is the top of `/`, or that it is per project at `/p/{owner}/{repo}`.
  Ruled 2026-10-26 by the maintainer: `/cockpit`, linked from the start page and the project pages.
- Q-S0010-5 Order and folds: the criteria keep the order of the data and apply the SPEC-0008 fold (a part over 5 lines per project, its lines in a details element, the number from the data's list length). The page would then count lines; confirm that this is allowed here or rule that the data states the number.
  Ruled 2026-10-26 by the maintainer: the fold counts the lines of a list. That is layout, not a figure.
- Q-S0010-6 Freshness: the criteria show "as of {as_of}" and apply no rule over age. Confirm, or rule a limit (for example data older than a day is "not known yet") and where the limit is set; a limit would make the page compare dates.
  Ruled 2026-10-26 by the maintainer: no age limit. "as of {as_of}" comes from the data.
- Q-S0010-7 Labels: the criteria fix the six router labels review, fix, ci-red, conflict, approve and ready as a closed list and refuse a document with another key. Confirm, or rule that an unknown label is ignored or shown.
  Ruled 2026-10-26 by the maintainer: exactly the six router labels, a closed list. A new label is a new schema.
- Q-S0010-8 A count of 0 in the strip: the criteria show it (a known value). Confirm, or rule that it is muted as in SPEC-0009 rule 4.
  Ruled 2026-10-26 by the maintainer: a 0 is shown, muted, as in SPEC-0009 rule 4.
- Q-S0010-9 A person with a project that has nothing waiting: the criteria show the project in the strip and omit it from the other two parts. Confirm, or rule that a project with nothing waiting is not shown at all, or that the empty phrase is shown per project.
  Ruled 2026-10-26 by the maintainer: a project with nothing waiting is in the strip only.
