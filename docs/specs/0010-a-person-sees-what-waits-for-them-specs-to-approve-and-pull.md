# SPEC-0010: A person sees what waits for them and opens it on GitHub

- Status: Draft
- Owner: maintainers
- Requirements: REQ-110

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence, as data: "A person sees what waits for them: specs to approve and pull requests ready to merge, each with its verdict, and opens them on GitHub from the page." It is the issue #64 brief of the maintainers (2026-10-25), whose five answers are the conductor's proposals, each open to the maintainers' ruling in the questions below. In agk a person approves every spec (an `Approve: <head> SPEC-<n>` comment) and merges every pull request; the router labels a pull request `agk:approve` or `agk:ready` when it waits for a person, and the weekly report shows "Ready to merge" only once a week, which is too late for work that is ready now. The principles that bind every rule: the page stays read-only (a link opens GitHub; no button merges, approves or comments); it reads only what the project publishes or what GitHub shows publicly; no token is in the page; nothing names one project. Where the brief leaves a point open, this spec takes the most conservative reading and records the point as a question; none of the questions is answered here.

## Rules

1. **The cockpit.** A signed-in person's cockpit (its address is Q-S0010-4) shows three parts in this order, each under its fixed heading: "Needs your merge", "Specs to approve", "In the pipeline". Each part is built from the projects of SPEC-0001 rule 1 (the repositories on which the App is installed and that the person can read), in the order of that list, and shows nothing of a repository the person cannot read. A part groups its lines under the project's name (`owner/repo`). The cockpit is read-only (rule 8).
2. **The pipeline data.** For each project the page reads one document, the pipeline document, published by the project (the conservative reading of the brief's open point 4, Q-S0010-1 and Q-S0010-2): it is read with the signed-in person's own token and the App's two declared read permissions (SPEC-0004 rules 6 and 7), so no permission is added, the portal reads no pull request, label or comment itself, and the browser reads nothing. Its schema is agk's and is not written yet; the page needs from it only: `schema`, the time it is `as_of`, a `ready` list (per item: the pull request `number`, the `verdict` first line, a link to the pull request on GitHub), an `approve` list (per item: `number`, `spec` as `SPEC-<n>`, a link) and `counts`, an object with exactly the six keys `review`, `fix`, `ci-red`, `conflict`, `approve` and `ready`, each an integer from 0 or `"unknown"`. The page checks the document against a closed list as SPEC-0005 rule 13 does the report: an extra or missing key, a wrong type, an `unknown` where the list does not allow it, or a `schema` it does not read makes that project "not known yet" with the reason; a `schema` that is an integer the page does not read says so, as SPEC-0005 rule 13 does. The fields above are proposals for agk's schema; this spec is amended when agk writes it.
3. **Needs your merge.** One line per item of `ready`, in the order of the data: "PR #{n}: {verdict}" with the whole line linked to the pull request. `{verdict}` is the first line of the latest clearing verdict as the data gives it, escaped and cut at 120 characters with an ellipsis (Q-S0010-3). The title of the pull request is not shown (SPEC-0005 rule 10).
4. **Specs to approve.** One line per item of `approve`, in the order of the data: "PR #{n} asks for approval of {spec}" with the whole line linked to the pull request. `{spec}` is the data's `spec`, accepted only if it has the shape `SPEC-` and four digits and otherwise the project's item is "{What} could not be read: not known yet." (SPEC-0005 rule 10).
5. **In the pipeline.** One strip per project: "{project}: review {n}, fix {n}, ci red {n}, conflict {n}, approve {n}, ready {n}", each count the data's own, in this order, a count of `"unknown"` reading "not known yet" in its place; it is a count and never a list, and the page adds nothing up. A count of 0 is shown (Q-S0010-8).
6. **Empty and unknown.** A part whose lists are empty for every project says "Nothing waits for you." (the strip is never empty). A project with no pipeline data, with data that cannot be read, or whose read failed stands under each part with "{project}: not known yet: {reason}", with no number of it, never as zero and never as an empty part; a failure of one project is that project's and stops no other (SPEC-0001 rule 6). The page computes no count: a number is shown only if the data states it.
7. **As of.** Each project's block shows "as of {as_of}" with the data's own value, placed as it is; no age is computed from it and no data is hidden for being old (Q-S0010-6).
8. **Read-only, and the links.** The only way to act is a link. A link is shown only if its address starts with `https://github.com/` and holds no space or quote (SPEC-0005 rule 9); any other address is not shown and the line stays as text. There is no form that changes anything, no button that merges, approves or comments, no script, no token in the markup, and the server makes no call to GitHub that writes (SPEC-0001 rule 3, SPEC-0004 rule 8). Nothing names one project: no project, owner or repository is written in a file of this repository.
9. **The look and the security.** SPEC-0008 applies in full (tokens, classes only, native controls, a 44 px target, one column at 360 px without a horizontal scroll, a fold over 5 lines of a part, Q-S0010-5) and so do SPEC-0004's headers; every text from the data is escaped.
10. **The fixed phrases.** These, and no other sentence, are shown: the headings "Needs your merge", "Specs to approve" and "In the pipeline", "Nothing waits for you.", "PR #{n}: {verdict}", "PR #{n} asks for approval of {spec}", the strip "{project}: review {n}, fix {n}, ci red {n}, conflict {n}, approve {n}, ready {n}", "as of {as_of}", "not known yet", and the reasons of SPEC-0001 and SPEC-0005 rule 13 for a project that cannot be read.

## Tests

- Rule 3: each item of `ready` is one line with its number, the escaped and cut verdict and the link, in the order of the data, and no title; REQ-110 AC1.
- Rule 4: each item of `approve` is one line with its number, its spec and the link; a spec of another shape is the unknown line; REQ-110 AC2.
- Rule 5: the strip shows the six counts in order, an unknown count reads not known yet, and no list is shown; REQ-110 AC3.
- Rule 6: empty lists say "Nothing waits for you.", and a project with absent, unreadable or failed data stands with not known yet and its reason, never as zero; REQ-110 AC4.
- Rules 1, 2 and 8: no form, button or script is in the markup, no token is in the page, a link not of GitHub is not shown, the server makes only reads with the person's token, and only the projects of the person's list are shown; REQ-110 AC5, REQ-110 AC6.
- Rule 7: the as-of is the data's own and no age is computed; REQ-110 AC7.
- Rule 9: the tokens, no script, no style attribute, native controls, 44 px and 360 px; the headers are unchanged; REQ-110 AC8.
- All tests use fixtures of saved responses and no network.

## Open questions

- Q-S0010-1 The brief's open point 4: where does the data come from? The facts are these. The App has exactly the permissions Actions read and Metadata read, and the server refuses an installation with any other (SPEC-0004 rules 6 and 7); GitHub's labels and comments of a pull request need Pull requests read (verify), so reading them from the server needs a SPEC-0004 amendment, a new App permission that every installation must accept, and an update of the permission check. Reading GitHub's public API from the browser is excluded by SPEC-0004 rules 1 and 2 and SPEC-0008 (strict policy, no script), reads public repositories only and shares one anonymous rate limit. Publishing a document in a workflow artifact needs no new permission (the portal already reads artifacts) but needs agk to write it. The criteria assume the last: the project publishes the pipeline document. Confirm, or rule the server read (with the permission amendment) or another source.
- Q-S0010-2 If the project publishes it: under what name and how often? The weekly `agk-facts-<week>` artifact is the wrong carrier for work that is ready now (it is made once a week), and SPEC-0001 rule 2 refuses an archive with a third entry. The criteria assume a separate artifact of its own (name to be fixed by agk, for example `agk-pipeline`), the latest unexpired one read as the facts are, written by the router or a scheduled job at a cadence agk chooses; schema 6 of the report does not change. Confirm, or rule another carrier, and say who writes agk's requirement and schema (the portal's build waits for it and for a golden of it).
- Q-S0010-3 The verdict line is free text from a comment. The criteria show the first line, escaped and cut at 120 characters. Confirm, or rule that only a fixed word ("cleared", with the head) is shown, or another length.
- Q-S0010-4 Where is the cockpit? The criteria put it at its own address `/cockpit`, linked from the start page and the project pages. Confirm, or rule that it is the top of `/`, or that it is per project at `/p/{owner}/{repo}`.
- Q-S0010-5 Order and folds: the criteria keep the order of the data and apply the SPEC-0008 fold (a part over 5 lines per project, its lines in a details element, the number from the data's list length). The page would then count lines; confirm that this is allowed here or rule that the data states the number.
- Q-S0010-6 Freshness: the criteria show "as of {as_of}" and apply no rule over age. Confirm, or rule a limit (for example data older than a day is "not known yet") and where the limit is set; a limit would make the page compare dates.
- Q-S0010-7 Labels: the criteria fix the six router labels review, fix, ci-red, conflict, approve and ready as a closed list and refuse a document with another key. Confirm, or rule that an unknown label is ignored or shown.
- Q-S0010-8 A count of 0 in the strip: the criteria show it (a known value). Confirm, or rule that it is muted as in SPEC-0009 rule 4.
- Q-S0010-9 A person with a project that has nothing waiting: the criteria show the project in the strip and omit it from the other two parts. Confirm, or rule that a project with nothing waiting is not shown at all, or that the empty phrase is shown per project.
